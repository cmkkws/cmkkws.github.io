문서 구조 요소별 9종 어블레이션 설계

JATS XML 구조 파서가 생성하는 각 요소가 LLM 수치 귀속 정확도와 토큰 소모에 미치는 영향을 분리 측정하기 위해 **단계적 누적 5종(L0L4)**과 **단일 요소 제거 4종(LOO-1LOO-4)**을 설계했다.

개발 93편 실측 토큰 통계 (`tiktoken: cl100k_base`)

1차 개발 후보 93편 전체(parsed-dev-93/papers/PMID*.json, 대·소목차 역할 분류 결과 포함)를 9개 직렬화 버전으로 변환해 실제 BPE 토크나이저(tiktoken cl100k_base)로 토큰 수를 계측했다.

  • 공통 포함 범위: 논문 제목(title) + 초록(abstract·trans-abstract) + 본문(body) + 별도 표·그림 영역(floats-group)
  • 공통 제외 범위: 참고문헌·사사 목록(back)은 9종 비교에서 모두 제외하고, 별도 참고 행으로 원문 부하를 측정했다.
  • 문맥 한도 기준: 순수 입력 텍스트 기준 4K(4,096), 8K(8,192), 16K(16,384), 40K(40,960) 초과 편수를 집계했다. (추론 시 출력 예약 1,024 + 64토큰을 제외하면 안전 한계는 더 낮아진다.)

1) 단계적 기능 ON (L0 → L4) 토큰 분포

2) 풀 구조(L4)에서 단일 옵션 OFF (LOO-1 ~ LOO-4) 변화

3) L4-Compact 이중 ID 경량화 실측 및 참고 비교군

L4의 정보와 추적성을 유지하면서 프롬프트 토큰을 줄이기 위해 **저장·채점 DB용 전역 ID(PMID...:경로)**와 **LLM 프롬프트 입력용 단축 ID(D1·[p1]·[t1] + 표 내부 [r,c] + 열·행 헤더 역인덱스 1회 선언)**를 분리하는 이중 매핑(L4-Compact)을 구현해 검증했다.

  • 무손실 역복원 검증: 93편 총 20,367개 표 셀에서 (r, c) 좌표 충돌 0건, 역인덱스 헤더 복원 불일치 **0건**으로 원본 전역 node_id 100% 복원 확인.
  • 실제 서버 여유 한계: L4-Compact 최장 논문 1위(PMID 41893183: 48,088토큰)와 2위(PMID 37430291: 29,853토큰)의 격차가 커서 32K(32,768)·38K·40K(40,960) 어느 기준에서도 **40K 초과 편수는 93편 중 단 1편(PMID 41893183)**으로 동일하다.

계측 결과 해석, 이중 ID 설계 근거 및 RAG 3원칙

1) 실측 수치에서 확인된 핵심 결과

  1. 기본 서버(4K/8K)에서는 L0조차 전문 투입 불가: 가장 가벼운 평면 마크다운(L0)도 93편 중 86편(92.5%)이 4K를 초과하고 33편(35.5%)이 8K를 초과한다. L4-Compact 역시 4K 초과 91편, 8K 초과 62편으로 기본 서버에서는 RAG 청킹이 필수다.
  2. 오른쪽 꼬리 역설 및 로컬 40K 초과 14편 → 1편: L0 → L4 증가폭이 평균 3.49배인데 P90에서는 5.77배(10,490 → 60,529)로 뛰어, 표가 크고 복잡한 핵심 임상 논문일수록 40K 상한에 먼저 걸려 잘리는(14/93편) 역설이 있었다. L4-Compact는 이를 평균 -52.2%(12,220토큰)·P90 -68.1%(19,287토큰)로 줄여 노드 ID를 끈 LOO-4(평균 14,234)보다도 가볍고 92/93편(98.9%)이 32K·40K 이내로 들어온다.
  3. 토큰 주범은 node_id(44.3%)와 headers(29.9%), 가성비 최강은 notes·<xref>(합 2.6%): 표 각주(notes)와 본문 <xref>·배정 연결은 합쳐도 평균 **~679토큰(2.6%)**만 쓰므로 항상 유지한다.
  4. 40K 전문 vs 2K~8K RAG 역할 분리 (어텐션 희석 및 실험 변별력): 입력 \(N\)이 4K에서 32K~40K로 늘면 Softmax 확률 총합(\(1\)) 안에서 무관한 배경 문장·타 시점 표로 어텐션이 분산되고(Lost-in-the-Middle), 유사 오답 표와의 혼동이 커지며 Prefill(\(O(N^2)\))·KV 캐시 부담도 급증한다. 또한 30K~40K로 예산을 풀면 L4-Compact(평균 12,220) 기준 검색기 성능과 무관하게 전문이 통째로 들어가 검색·청킹 모듈의 변별력이 사라진다. 따라서 40K 전문은 No-Retrieval 기준선, 2K / 4K / 8K RAG는 가성비 최적 구간(Sweet Spot) 탐색용 고밀도 선별 파이프라인으로 역할을 분리한다.

2) 타 도메인 선행연구 기반 L4-Compact 이중 ID 설계 근거

  • 저장 DB vs 프롬프트 입력 분리 (ALCE · LongCite · WebArena · SpreadsheetLLM): RAG 인용 벤치마크(ALCE, LongCite)와 웹 DOM 에이전트(WebArena)처럼 원문 전역 경로(PMID...:1/4/2/0/1, DOM XPath와 동일 구조)는 저장소에 두고 프롬프트에는 짧은 순번([p1], [t1])만 노출해 양방향 딕셔너리로 역복원한다. 표 내부는 SpreadsheetLLM(arXiv:2407.09025)의 역인덱스 압축처럼 셀별 중복 대신 열·행 단위 헤더 범위를 1회만 선언한다.
  • 대안 포맷(LTEM·중첩 트리 JSON·상대 경로 문자열) 대신 채택한 이유: LTEM(확장 마크다운)은 L0(평면 .md) vs 구조 보존 비교 축을 흐리며, 중첩 트리 JSON은 표 형태마다 깊이가 달라져 [r,c] ↔ 원본 node_id 1:1 역추적이 끊긴다. 반면 [p1]/[t1] + [r,c] + 열·행 헤더 역인덱스는 parse_jats.py의 2차원 cells 출력과 100% 무손실로 맞물린다.

구조적 청킹, 표 317개 실측 분포 및 검색기 비교 설계

1) 개발 93편 내 표(table-wrap) 317개 크기 분포와 Small-to-Big 청킹

RAG의 **2K / 4K / 8K 한도는 청크 1개 크기가 아니라 검색된 근거 청크들의 합(Total Token Budget)**이다. 개발 93편의 모든 표(317개)를 L4-Compact 기준으로 계측한 결과, 일반 표(중앙 1,191토큰)는 2K에서 표 1개 내외, 4K~8K에서 문단·다중 표와 함께 들어가지만 극소수 초대형 표가 별도 분할 규칙을 요구한다.

  • 최대 단일 표 사례: PMID 31752813 Table 7(47행, 12,541토큰), PMID 35103799 Table 1(20행, 9,026토큰), PMID 36339386 Table 3(50행, 8,980토큰) 등 3개 표는 표 1개만으로 8K를 초과한다.
  • 검색용 인덱스 vs LLM 본체 분리 (Small-to-Big): 표는 수치(td)가 많아 임베딩 모델(512토큰 상한 등)에 통째로 넣으면 뒷행·각주가 잘리거나 숫자 잡음에 신호가 희석된다. 따라서 **검색 인덱스는 절 제목 + 표 캡션 + 다단 머리글 + 각주 + 문자 셀(150~400토큰)**로 작게 색인하고, 검색에 당첨된 표만 **L4-Compact 표 본체(중앙 1,191토큰)**를 꺼내 LLM에 전달한다.
  • 거대 표 행 분할 Fallback: 단일 표가 단일 청크 상한(예: 3K) 또는 잔여 토큰 예산을 초과하면 임의 문자 절단 대신 행(row) 블록 단위로 쪼개되, 각 조각 상단에 다단 열 머리글과 하단에 표 각주를 자동 복제해 문맥 훼손을 방지한다.

2) 검색기 비교 설계: 어휘(BM25) vs 범용 SOTA(Qwen3-Embedding) vs 도메인 특화(MedCPT)

BM25 단독, 임베딩 단독, 그리고 BM25 + 임베딩 RRF 하이브리드를 동일 청크·동일 토큰 예산 하에서 비교한다. 특히 어휘 검색을 BM25가 담당하므로, 밀집(Dense) 임베딩 축에서는 기존 BGE-M3 단일안 대신 범용 최신 SOTA와 의생명 도메인 특화 모델 2종을 정면 대조한다.

  • 공정 비교 통제: MedCPT의 512토큰 한계(기존 PubMedBERT와 동일)에서 뒷부분 절단이 발생하지 않도록, 문단 청크(200~450토큰)와 표 검색 인덱스(150~400토큰)를 두 모델에 동일하게 입력한다.

3) RAG 공정 비교와 토큰 통제 3원칙

  • 실측 토큰 및 절삭률 동시 보고: 정확도(All-fields EM)만 비교하지 않고 실제 입력 토큰 수, 토큰당 정확도, 문맥 상한 초과로 인한 절삭 건수를 함께 기록한다.
  • 표현 형식(L0~L4·L4-Compact)과 청킹 전략 분리: 동일 근거 구간(또는 오라클 스팬)에서 구조 포맷 효과를 먼저 분리 측정하고, 고정 길이(Fixed-size) 대비 계층 구조(Structural) 청킹의 표·각주 경계 보존 효과는 별도 축으로 비교한다.
  • Top-K 개수 대신 2배 간격 총 토큰 예산(2K / 4K / 8K + 전문) 비교: 같은 Top-K=5 청크라도 L0과 L4의 토큰 부피가 수배 차이 나므로 총 토큰 상한을 고정해 정보량 편향을 차단한다. 또한 4K/6K/8K처럼 조밀한 구간은 모두 93편 평균(12,220토큰) 미만에서 포화·잡음 차이를 구분하기 어렵고, 단일 표 중앙값이 1,191토큰이므로 2K (2,048 · 희소 한계: 표 1개+배정 1~2문단) → 4K (4,096 · 균형점) → 8K (8,192 · 여유·포화 확인) → 전문(L4-Compact) 기준선의 2배 간격 4점으로 부족 → Sweet Spot → 포화·어텐션 희석 곡선을 측정한다.

가성비 예산 확정 이후 실행 비교(`27B` vs `8B`) · `Thinking` · 파레토 시각화 계획

6단계에서 가장 비용 대비 성능이 좋은 RAG 토큰 예산(Sweet Spot)을 먼저 확정한 뒤, 7단계 추론 파이프라인에서 로컬 자원 활용 방식과 생성 전략(Thinking ON/OFF)을 교차 대조한다.

1) 오프라인 사전 임베딩 전제와 실행 구성 대조 (방법 A vs 방법 B)

  • 문헌 임베딩의 오프라인 일회성: 청크 임베딩은 코퍼스 전처리 단계에서 **사전 계산(Offline indexing)**해 두고, 추론 시에는 짧은 질의(Query) 1건만 임베딩하므로 신규 문헌 단건 파이프라인을 제외하면 전체 실험 시간에서 임베딩 비중은 작다. 반면 RTX 4080 SUPER (16GB VRAM) 단일 GPU에서 대형 생성 모델(27B Q4_K_M)과 GPU 임베딩 모델을 동시에 상주시킬 수는 없으므로 아래 두 실행 구성을 비교한다.

2) 추론 모드(Thinking ON/OFF) 2×2 대조 및 출력 스키마 주의점

  • Thinking OFF (enable_thinking=False): 채팅 템플릿 말단에 빈 <think>\n\n</think>\n\n를 프리필해 즉시 규격 JSON을 생성한다. 출력 토큰이 짧아 빠르며 response_format JSON Schema 제약과 충돌하지 않는다.
  • Thinking ON (low / medium, max_tokens 확장): 최종 JSON 전에 <think> 블록에서 비교군 열 순서·단위(안구 vs 환자)·시점·분석 분모를 먼저 검산한다. 단, 출력 토큰 증가로 생성 시간이 크게 늘어나고 기존 1,024토큰 상한에서는 JSON 미완성 절단이 발생할 수 있어 max_tokens를 넉넉히 확보하고 1건 호환 테스트(response_format vs <think>)를 거친 뒤 적용한다.

3) 성능 vs 토큰량 비교 그래프 설계 (실측 후 반영)

  1. 입력 토큰 예산 곡선 (X축: 2K / 4K / 8K / 전문 L4-Compact, Y축: All-fields EM): 8B와 27B가 어느 입력 예산에서 최고 효율을 찍고 희석·포화되는지 비교한다.
  2. 총 소모 토큰·시간 파레토 차트 (X축: 입력 + <think> + JSON 출력 총 토큰 수 및 문항당 초, Y축: All-fields EM): 8B OFF · 8B Thinking ON · 27B OFF · 27B Thinking ON 4개 조합의 비용-성능 파레토 경계를 시각화한다.

출력 JSON 스키마 v1 확정 및 4대 진단 채점 체계

벤치마크 정답 구조(answer_records_for_review.json)와 1:1 대응하면서, 8B/27B 비교와 L0~L4-Compact 공정 평가에서 출력 절단·채점 왜곡을 막기 위한 출력 JSON 스키마 v1과 오류 진단 채점기(attribution-eval-v1)를 확정·구현했다.

1) 스키마 v1의 5가지 핵심 설계 결정

2) 4대 핵심 진단 채점 사례 및 Thinking 호환 실측

실제 RAG 추론에 앞서, 연구의 핵심 가설을 가르는 4대 실패 사례를 단위 테스트(test_scorer_v1.py, 개발 12편 실데이터 포함 9건)로 검증했고, 로컬 Qwen3.8-27B-Q4_K_M 서버(b10549)에서 Thinking 3조건 실측도 완료했다.

93편 산문 흐름, `Coord-Row` 압축 및 `dev-8` 오프라인 검색 실측 (BM25 · Dense · 2×2 Rerank)

청커·패커 구현에 앞서 개발 93편의 표·각주 제외 산문 흐름과 Coord-Row 표 직렬화 압축을 실측하고, 구현된 5단계 파이프라인(rag_pipeline.py·eval_retrieval.py·eval_dense_rerank.py, 단위 테스트 16/16 통과)으로 dev-8 BM25 기준선 및 GPU CUDA Dense + 2×2 리랭크 9종 리콜을 실측했다.

1) 93편 순수 산문(Prose) 흐름 통계 (표·그림·각주·back 제외)

  • 거시 흐름: 92/93편(98.9%)이 서론(제목 있음 79 + 무제목 도입 13) → Methods(92) → Results(92) → Discussion(91) IMRaD 순서를 따른다 (단 1편은 Results→Discussion→Methods 역순 변형). 전체 산문(초록+본문)은 **중앙 5,312토큰(평균 5,553.2, 최대 11,882)**이다.
  • 구역별 비중 및 소제목 구조: Introduction(중앙 657) + Discussion(중앙 1,451)이 산문의 ~40%를 차지하는 반면, 핵심 근거 구역은 Methods(중앙 1,487)와 Results 줄글(중앙 905)이다. Methods는 66/92편(71.7%)이 소제목을 사용하며 최하위 구역 중앙값이 214토큰(461개 중 <200 215개), Results는 40/92편(43.5%)만 소제목을 쓰고 나머지는 통짜 7문단(중앙 905토큰)으로 이어진다. Abstract(중앙 412토큰)는 69/93편(74.2%)이 Purpose/Methods/Results/Conclusion 구조화 소제목을 보유한다.

2) 도메인 결합 표 압축 (Coord-Row: SpreadsheetLLM + TOON 파이프 + ALCE [r,c])

셀마다 딕셔너리 키({"r":..,"c":..,"kind":"td","text":..})를 반복하는 대신, **상단 다단 헤더 역인덱스(SpreadsheetLLM) + 1행 1줄 파이프 정렬(TOON) + 셀 앞 [r,c] 인라인 좌표(ALCE)**를 결합하고 셀 내부 줄바꿈을 정규화했다. 전체 317개 표(20,367개 셀) 무손실 검증에서 좌표 불일치 **0건**을 통과했다.

3) RAG 5단계 세부 알고리즘 (1~5단계 구현 및 디스크 캐시 구성)

  1. 구조 청커: 소제목 경계를 넘지 않는 200~450토큰 문단 병합(초과 문단 1문장 겹침 분할) + Small-to-Big 표 검색 인덱스(<=400토큰)로 93편 총 2,917청크 구축(산문 2,626 중앙 224 / 표 인덱스 291 중앙 194·최대 400, >512 0개).
  2. 질의 생성·확장: Single Query 대비 Title+Abstract 괄호 약어·설계 단서(301건, LLM 토큰 0 소모)를 결합한 Multi-Query (Q_outcome 0.7 : Q_design 0.3) 가중 RRF 융합.
  3. 이원화 2×2 리랭크: Q_design 기반 Methods 점수는 보존해 배정·단위 문맥 밀림을 막고, Q_outcome 상위 20개 후보를 MedCPT-Cross-Encoder vs Qwen3-Reranker-0.6B로 재정렬.
  4. 예산 패커: ① Title만 고정(Abstract는 검색 경쟁), ② Methods 최소 1~2청크 보호, ③ Coord-Row 표·각주 원자성 및 초과 표 행 블록 분할+헤더/각주 복제, ④ 선정 표 <xref> 인용 문단 보충 후 Title → Methods → Results → Tables 원순서 재정렬.
  5. 오프라인 벡터·컨텍스트 캐시 (build_eval_cache.py): 16GB 단일 GPU에서 LLM 생성(27B)과 임베딩 경합을 피하기 위해 93편 전체 문서 벡터(.npz, MedCPT 10.75s · Qwen3-Embedding-0.6B 25.65s)와 dev-8 사전 패킹 컨텍스트(@2K/@4K/@8K · Oracle 635~2,191 · Full L4-Compact 6,483~21,105토큰)를 디스크에 사전 저장.

4) dev-8 CUDA GPU 9종 검색·2×2 리랭크 오프라인 리콜 실측

93편 전체 2,917청크 기준 GPU 소요 시간은 BM25 0.002s, MedCPT 문서 1.29s·질의 0.02s, Qwen3-Embedding-0.6B 문서 3.11s·질의 0.08s, 8문항 리랭크 MedCPT-CE 0.69~0.83s, **Qwen3-Reranker-0.6B 2.68~2.89s**이다. (Oracle 기준선 평균 1,509.6토큰·회수율 100%)

  • 핵심 관찰 및 LLM 본 실험 대표 후보 선정: @4096에서 **MedCPT+BM25(4번)**가 표·셀 회수 **100%**를 가장 안정적으로 잡고, **Qwen3-Embedding(3·5번)**은 산문 회수(@4K 0.812, @8K FULL 0.875)에서 우세하며, Qwen3-Reranker-0.6B 결합 조합(7번·8번)이 @4096 최고 완전 회수율(FULL=0.625, 5/8)을 기록했다. 차기 LLM 추출 비교는 변별력이 가장 뚜렷한 @4096 주축으로 1_bm25_multi · 4_hybrid_bm25_medcpt · 5_hybrid_bm25_qwen3 · 7_rerank_qwen3_to_qwrr_sota · 8_rerank_medcpt_to_qwrr_cross 및 Oracle·Full L4-Compact를 대조한다.
